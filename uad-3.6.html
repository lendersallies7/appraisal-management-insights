If you read nothing else: the mandate is keyed to submission date, and an update report must match the format of the report it amends.

Those two facts generate most of the edge cases below.

§1

What actually changes

The report stops being a form#

UAD 2.6 was a dataset bolted onto fixed forms. Each property type had its own form, and the form determined the fields. UAD 3.6 inverts that: there is one dynamic URAR, and the assignment determines which sections appear.

For an engineer this is the whole story. You are no longer mapping to a known rectangle. Code that assumes a 1004 has a fixed grid of three comparables in fixed positions will not survive contact.

Consequences, in rough order of how much code they touch

  • The sales comparison grid is dynamic. Comparable count varies. Do not hard-code column counts, and do not assume positional stability between versions of the same report.
  • Addenda largely go away. Commentary that used to land in a free-text addendum now sits in the relevant section. Parsers and review rules that scrape addenda for keywords are about to find nothing.
  • Condition and Quality split into interior and exterior ratings. Any rule, scorecard or warehouse column keyed to a single C/Q rating needs a decision: which one, or both.
  • Manufactured homes get C and Q ratings, which they did not have under 2.6. If your analytics treat missing C/Q as a manufactured-home signal, that heuristic dies.
  • Inspection type comes from the engagement letter, specified by the client, not inferred from the form number. If your system derived scope from the form code, that derivation no longer has an input.

The part most teams under-scope#

The migration gets planned as a parsing change. It is really a schema change in your collateral data store, and those propagate — review rules, QC scorecards, investor overlays, exception reporting, anything downstream written against 2.6 field names.

Budget for the downstream. The parser is the easy part.

  • A loan carrying a UAD 2.6 report can still be sold to the GSEs after 2.6 retirement. Retirement governs new submissions, not existing collateral. Do not build a hard block that rejects 2.6 reports from your pipeline on 2 November.
  • Lenders may stage their own rollouts. If you serve multiple lenders, requirements will differ by lender and by assignment during the transition. Build for per-client configuration, or you will be hot-patching through October.
§3

UCDP rules that will bite you

These are the ones that generate support tickets.

Document File ID is version-locked#

UCDP does not accept 2.6 and 3.6 under the same Document File ID. An update or completion report must match the format of the original. Your order record needs to carry the UAD version of the original submission and enforce it on every amendment — not read the current default.

Document File IDs do not transfer between lenders#

A lender cannot reuse a Document File ID created from another lender's submission. For transferred loans, the receiving lender may use the transferring lender's DocFile ID and SSR when delivering the loan — a different operation from submitting. Model those as two distinct cases; conflating them produces rejections that are painful to diagnose.

Reuse and retention#

Reusing an appraisal under a new loan number is permitted only where GSE policy allows. The loan number can be changed in the Portal or through Direct Integration.

Construction lending

Retain Form 442 / 1004D or an accepted alternative in the loan file for the life of the loan. This is a retention requirement, not a submission one — check your document retention policy, not just your submission path.

§4

Validation

The UAD Compliance API validates XML for completeness, validity and reasonableness against the UAD Delivery Specification. Two things to be clear about.

  • It is not Collateral Underwriter and not Loan Collateral Advisor, and returns neither's findings. A file that passes the Compliance API can still draw CU messaging. If your UI says "appraisal validated," make sure everyone knows which validation.
  • The rule sets live in Appendices H-1, H-2 and H-3 of the specification. Read them before writing your own pre-flight validator — a large share of what teams build by hand is already enumerated there.
Recommendation

Run the Compliance API as a pre-submission gate inside your own pipeline, not only at UCDP. Catching a malformed file before it reaches the portal turns a multi-party support thread into a local error message.

§5

ULDD Phase 5

Easy to miss, because it sits with a different team.

Loan delivery must implement ULDD Phase 5 v5.1.0, which aligns property data points with UAD 3.6. The GSEs publish a job aid for the alignment.

If appraisal integration and loan delivery are separate squads in your organisation, this is the seam where the mandate gets dropped. Confirm ownership explicitly.

§6

FHA, VA and USDA

Each runs its own implementation plan. Do not assume the GSE date applies to government lending — contact each agency. If your platform serves government channels, this is a per-channel configuration, not a global flag.
